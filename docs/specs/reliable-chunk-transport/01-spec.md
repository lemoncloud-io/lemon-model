## 범위
이 문서는 **계약**(보장·scope)을 고정한다. 모델링·흐름은 [02-design.md](./02-design.md) 참조.

## 핵심 결정

| 결정 | 계약 | 이유 |
|---|---|---|
| 제공 형태 | **기존 JSONTransport에 신뢰 모드를 내장**한다(옵트인 플래그). 별도 데코레이터·병렬 transport를 신설하지 않는다 | 작성자 결정 — 사용처 진입점을 하나로 유지(두 transport 공존의 혼동 제거), 청킹 구현 1벌 유지 |
| 옵트인 | 신뢰 모드를 켜지 않은 기존 사용자에게는 동작·와이어·기존 공개 API의 의미가 변하지 않는다. 기존 `src/socket` spec 전체가 회귀 기준선이다 | 00 옵트인 요구 — "기존 사용자 코드는 수정 없이 그대로 동작" |
| 보장 대상 | 신뢰 모드가 켜진 JSONTransport의 `send(value)` 호출 전부. 큰 값은 기존 청킹으로 분할되며, 작은 값(단일 manifest)도 같은 보장을 받는다. **Peer 경로도 포함한다** — Peer가 신뢰 모드를 옵트인하면 Peer의 메시지 송수신도 같은 보장을 받는다(Peer 송신 경로가 신뢰 모드 JSONTransport를 경유하도록 수정) | CTO 요구 (1) 일반 유실과 (2) 청크 누락을 하나의 계약으로 통합. Peer 포함은 작성자 확정(2026-07-13) |
| 페이로드 범위 | 보장 표면은 JSON 값 API다. 값에 실리는 내용(직렬화 가능한 모든 것, 인코딩된 바이너리 문자열 포함)과 무관하게 같은 보장을 적용한다. 저수준 문자열/바이너리 전용 신뢰 계층은 이번 범위 밖이다 | 작성자 결정 — 내장 방향 확정에 따른 조정. 00의 "페이로드 종류 무관"은 값 수준에서 성립 |
| 전달 의미론 | 와이어에서는 중복 전송(at-least-once)을 허용하고, 수신 상위에는 전송 단위당 완성본을 정확히 한 번(exactly-once) 전달한다. 중복 흡수는 청크 유무와 무관하게 전송 단위 기준으로 동작한다 | 재전송 기반 복구의 표준 형태. 중복 흡수는 계층 책임 — 00 요구 |
| 전송 단위 | 보장·실패 통지·중복 판별의 단위는 `send(value)` 1건(= 기존 tid 1개)이다. 신뢰 모드의 tid는 송신 인스턴스 재생성·재연결을 가로질러 재사용되지 않는다(기존 로컬 카운터 기본값은 신뢰 모드에서 사용 불가) | 부분 성공이라는 모호 상태를 없앤다. 카운터식 tid는 경계에서 재사용되어 exactly-once를 깬다 — critic 반영 |
| 종결 기억 | 완성 또는 실패로 종결된 전송 단위의 식별자를 유한한 시한 동안 기억해, 종결 후 늦게 도착한 중복(재전송 잔여)을 조용히 흡수한다. 기억 시한도 유한하며, 송신 종결 기억과 수신 완성 기억은 별개로 관리한다 | 종결 즉시 상태를 지우는 기존 동작은 늦은 재전송을 재조립·재방출해 exactly-once를 깬다 — critic·양측 적용성 리뷰 반영 |
| 송신 성공의 정의 | 신뢰 모드의 `send(value)`는 종결을 알리는 `Promise<void>`를 반환한다. 성공은 수신측이 완성본을 상위로 방출했음을 확인한 시점이다. 복구 방식이 무엇이든 이 하한선은 지킨다. 반환 타입 확장(void→Promise)은 기존 호출부와 소스 호환이어야 하며, 반환값을 버리는 호출자 밑에서 미처리 rejection이 발생하지 않아야 한다 | 성공을 "송신 버퍼 투입"으로 약화하면 도착 보장이 무력화 — 작성자 확정. self-catch — 레이어 리뷰 반영 |
| 무결성 | 완성본이 원본과 동일함을 검증한 뒤에만 상위로 전달한다. 검증 실패는 유실과 동일하게 복구 대상이다. 검증 수단은 설계에서 정한다 | 조용한 손상 금지 — 00 요구 |
| 실패 종결 | 복구 시도는 유한하다(재시도 상한·시한). 상한 도달 시 해당 전송 단위를 실패로 종결하고 상위에 통지하며 부분 상태를 폐기한다. 일시적 전송 실패(재연결 구간 포함)는 즉시 종결 사유가 아니며 시한·상한 안에서 재시도된다. 상한·시한은 설정 가능하다 | 무한 대기 금지 — 00 요구. ReconnectingNetwork 조합 시 재연결 구간의 동기 throw를 종결로 오인하지 않기 위함 |
| 제어 메시지 | ACK·재요청 등 제어 패킷은 기존 `json:*` 패킷 계열의 확장으로 정의하며, 계층 내부에서 소비되고 상위에 노출되지 않는다. 제어 메시지 자체의 유실은 별도 보장 없이 재시도 시한·상한으로 흡수된다 | 제어 채널에 다시 신뢰 계층을 얹는 순환 차단 |
| 복구 방식 개방 | 복구 방식(누락 청크 선택적 재요청 vs 전송 단위 전체 재전송 w/ ACK)은 이 계약이 고정하지 않는다. 설계에서 결정하되, 어느 쪽이든 위 보장(exactly-once·수신 완성 확인·유한 종결)을 만족해야 한다 | 계약은 보장만 고정. 기존 설계 라운드의 NACK 하이브리드 수렴은 설계 입력으로 승계 |
| 모드 전제 | 송신자와 수신자 양단이 모두 신뢰 모드를 켠다(Peer 경로는 링크 양단의 Peer가 모두 옵트인). 한쪽만 켠 혼용 구성은 지원하지 않으며, 불일치는 조용한 오동작이 아니라 감지 가능한 에러로 드러나야 한다 | 재요청·ACK는 양방향 제어 패킷 전제. 플래그 불일치는 내장 방식의 고유 실패 모드 — 명시적 처리 강제 |
| Peer 경로의 관측 표면 | Peer 각 API(`send`·`post` 등)에서 전송 종결(성공/실패)을 어떻게 관측하는지는 설계에서 정한다. 단 하한선은 유지한다 — 실패가 조용히 삼켜지지 않고, 최소한 에러 통지로 드러난다 | Peer.send는 이미 응답(reply) 대기 의미론을 가짐 — 전송 보장과 응답 대기의 관계 정리는 모델링 몫 |
| 수정 범위 | `transport.ts`와 `socket.ts`(Peer 송신 경로의 신뢰 모드 경유에 필요한 최소 범위) 수정을 허용한다(이번 개정으로 종전 "기존 파일 무수정" 결정을 대체). 그 외 기존 파일은 무수정 원칙 유지(`index.ts` export 추가는 예외). 신뢰 모드를 켜지 않은 경로의 동작 불변이 수정의 경계다 | 작성자 결정 — 내장 방향 + Peer 포함 확정. 회귀 기준선은 기존 spec 전체(transport.spec·socket.spec 포함) green |
| 검증 | 기존 `transport.spec.ts`·`socket.spec.ts` 전체 green(무파손 회귀) + 신뢰 모드 시나리오 spec 추가(transport·Peer 경로 각각) + demo/socket-verifier 확장으로 유실 주입→복구, 복구 불능→실패 통지를 육안 확인 | 00 목표 + 내장 방식의 회귀 리스크 대응 |

## 모델 계약

송신 계약:

- 신뢰 모드의 `send(value)`는 전송 단위 하나의 종결(성공 또는 실패)까지 책임지는 `Promise<void>`를 반환한다.
- 재시도 상한·시한, 종결 기억 시한 등 복구 파라미터는 생성 시 설정할 수 있고, 합리적 기본값을 가진다.

수신 계약:

- 수신 상위에는 검증을 통과한 완성본만, 전송 단위당 정확히 한 번 전달된다.
- 청크 누락·손상은 수신측이 스스로 감지한다. 감지는 프로토콜에 내장되며 상위의 개입이 필요 없다.
- 복구 불능으로 종결된 전송 단위는 실패로 통지되고, 쌓여 있던 부분 상태는 폐기된다.
- 수신 검증은 필수 필드의 존재만 확인하고 미지 필드는 무시한다(forward-compat). 와이어 필드 추가는 하위호환 변경으로 취급한다.

순서 계약:

- 한 전송 단위 안에서 완성본은 원본과 동일하게 복원된다(청크 순서는 계층이 복원).
- 전송 단위 사이의 완성 순서는 송신 순서와 다를 수 있다. 재정렬은 보장하지 않는다.

## 서버 보장

- 보장의 양단은 신뢰 모드 JSONTransport를 실행하는 두 종단이다. 서버는 opaque 중계이며 무변경이다.
- 중계는 유니캐스트를 전제한다 — 송신자에게 에코백하지 않고, 의도한 상대에게만 전달한다. 보장은 1:1 논리 링크 단위로 성립하며, 에코백·브로드캐스트 릴레이는 허위 자기 수신과 무관 수신자의 오조립을 유발하므로 지원하지 않는다.
- stateless 서버(Lambda 등)는 종단이 될 수 없고 중계만 맡는다(인메모리 전송 상태가 invocation을 넘지 못한다). 상시 구동 서버는 연결별 신뢰 모드 JSONTransport로 종단이 될 수 있다.

## 클라이언트 동기화 계약

- 모델 동기화(model-sync) 경로는 신뢰 모드를 사용하지 않는다. 동기화의 신뢰성은 종전대로 스냅샷 재수신으로 해결한다.

## Out of Scope

- 모델 동기화 경로 적용.
- 저수준 문자열/바이너리 전용 신뢰 계층(NetworkSupportable 데코레이터형) 신설.
- 청크 페이로드의 압축·암호화.
- 전송 진행률 UI·콜백.
- dual-socket-network(이중 연결)와의 결합.
- 여러 전송 동시 진행 시의 대역 배분·우선순위 최적화.
- 전송 단위 간 완성 순서 보장.
- 한쪽만 신뢰 모드를 켠 혼용 구성과의 상호운용(감지·에러화는 하되 동작 보장은 없음).

## 재검토 조건

- 설계 결과 어느 복구 방식도 "수신 완성 확인" 하한을 만족하지 못하면 → 송신 성공의 정의·전달 의미론을 재검토.
- JSON이 아닌 저수준 페이로드(진짜 바이너리 프레이밍)에 도착 보장이 필요해지면 → 제공 형태(내장)·페이로드 범위 결정을 재검토(독립 계층안의 부활 검토).
- 신뢰 모드 off 경로의 동작 불변을 지킬 수 없는 수정이 필요해지면 → 옵트인·수정 범위 결정을 재검토.
- 재연결 후 이어받기(resume)가 요구로 확정되면 → 실패 종결(부분 상태 폐기) 결정을 재검토.
- 동기화 경로가 "최신만 재전송" 모드를 원하게 되면 → 클라이언트 동기화 계약과 00 비목표를 재검토.
- 멀티캐스트·브로드캐스트 릴레이 지원이 필요해지면 → 서버 보장(유니캐스트 전제)을 재검토.
- capability 자동 협상(`reliable: 'auto'` — 양단 신형이면 자동 활성, 구형 상대면 legacy 강등)이 요구되면 → 모드 전제·Out of Scope(혼용 구성) 결정을 재검토(2026-07-14 작성자 판단으로 이번 범위에서 명시 제외).
