## 핵심 결정

| 결정 | 계약 | 이유 |
|---|---|---|
| 제공 형태 | Network 계층의 합성 구현체 하나. `NetworkSupportable`을 준수하며, 완성된 `NetworkSupportable` **N개(2개 이상)의 배열**을 주입받는다. 2개 미만이면 생성 시 즉시 throw | 기존 데코레이터 관례(전체 멤버 위임)와 동일한 합성 방식. 각 소켓의 재연결·필터 등은 주입 전에 자유 조합 |
| 편의 생성 | 배열 대신 `{ count, networkFactory: (index) => NetworkSupportable }`로도 생성할 수 있다. 합성체는 소켓 생성을 소유하지 않고 소비자가 준 팩토리를 count만큼 호출만 한다 | 기존 `PeerNetworkFactory` 관용구(socket.ts:61)와 일치. 생성 소유가 합성체로 넘어가는 폐기안(02)과 구분 |
| 기본 전송 경로 | 표준 `send(data)`는 항상 첫 번째 소켓(메인, index 0)으로만 나간다 | 상위 계층(JSONTransport·Peer)이 표준 인터페이스로 얹혔을 때 동작이 단일 소켓과 동일 — 무파손 |
| 전체 전송 단위 | 호출 단위. 합성체 전용 확장 호출(`sendAll`)로만 전 소켓 전송이 일어난다. 모드 토글은 없다 | 전체 전송은 직접 소비자의 명시적 선택. 상위 transport의 청크가 의도치 않게 복제되는 경로를 구조적으로 차단 |
| 프레임 무변조 | 전체 전송은 동일 바이트 사본을 모든 소켓에 보낸다. 합성체는 식별자·봉투를 주입하지 않는다 | 상위 wire 포맷(JSONTransport 등)과의 충돌 원천 차단. 중복 판별 키는 소비자가 페이로드에 실은 것이 그대로 모든 사본에 실린다 |
| 확장 호출 실패 채널 | `sendAll`은 던지지 않는다. 각 소켓 전송을 독립 시도하고, 실패(미연결·연결 중·닫힘 포함)는 해당 소켓 index 태그를 담은 에러로만 전파한다 | 격리 철학과 일치 — 백업이 죽어 있어도 호출자 코드가 깨지지 않는다. 기존 send의 동기 throw 관례와 채널이 다름을 명시 |
| 소켓 독립성 | 한 소켓의 단절·에러·close는 다른 소켓들의 연결·송수신에 영향을 주지 않는다. 전체 전송 중 일부 실패 시 나머지 전송은 그대로 진행된다 | 00 요구사항 — 백업의 본질은 격리 |
| 수신 병합 | 전 소켓의 inbound는 하나의 `onMessage` 스트림으로 병합된다. 메시지 단위 출처 태깅은 하지 않는다 | 사용자 결정. 중복 걸러내기는 소비자 책임(식별자 기반)이므로 출처가 필수 아님 |
| 출처 구분 | 에러·수명주기 이벤트의 context에서만 소켓 index를 식별할 수 있다 | 단절·에러 대응(어느 쪽이 죽었나)에는 충분, 메시지 태깅의 침습 없음 |
| 무파손 | `src/socket` 기존 파일·공개 타입은 수정하지 않는다. 신규 파일 추가 + 신규 공개 심볼의 `index.ts` export 추가만 허용 | 옵트인 기능 — 기존 사용자 코드·테스트 기준선 유지 |
| 검증 | `src/socket` 하위 jest spec으로 계약을 회귀 가드하고, demo/socket-verifier 확장(2개 구성 시연)으로 다중 연결·전체 전송·중복 도착을 육안 확인한다 | 00 목표 — 검증 도구가 이미 실-전송 확인 수단을 갖춤 |

## 모델 계약

합성체의 `NetworkSupportable` 멤버 의미론:

- `send(data)`: 메인(index 0)으로만 전송. 실패 시 기존 관례대로 동기 throw.
- `sendAll(data)`(확장): 같은 data를 모든 소켓에 각각 전송. 호출 자체는 던지지 않는다 — 각 소켓의 전송 실패(미연결·연결 중·닫힘 포함)는 해당 index 태그를 담은 에러로만 전파되고, 일부 실패가 나머지 전송을 막지 않는다. 소비자 onError 핸들러가 throw해도 이 보장은 유지된다.
- `onMessage`: 전 소켓의 inbound 병합 스트림. 순서는 도착 순서이며 재정렬하지 않는다. 수신은 `readyState`와 무관하게 각 소켓이 살아 있는 한 계속된다.
- `onError`: 전 소켓의 에러를 모두 전파한다. 합성체가 구독 시점에 어느 소켓의 에러인지 판별해 context에 index 태그를 부여한다(내부 context 참조 동일성에 의존하지 않는다. 필드 형태는 설계).
- `close()`: 모든 소켓을 닫는다(멱등). 특정 소켓만 끊으려면 소비자가 주입한 해당 인스턴스를 직접 close한다 — 이것이 단일 소켓 강제 종료의 공식 경로다.
- 소비자가 스스로 수행한 명시적 close는 기존 네트워크 관례대로 이벤트를 발화하지 않는다. 출처 식별은 원격·비정상 단절과 전송 실패의 에러에 적용된다.
- `readyState`·`ready()`·`onOpen`: 메인(index 0)의 송신 가능 여부 기준. 백업들의 준비 여부는 합성체의 준비 상태에 영향을 주지 않는다(백업은 있으면 쓰고 없으면 못 쓸 뿐).
- `configure(options)`: 공통 옵션의 편의 전파(전 소켓). 소켓별로 다른 설정은 주입 전에 각 인스턴스에 직접 한다.

중복 판별 계약:

- 전체 전송된 사본들은 바이트 동일하다. 합성체는 새 식별자를 주입하지 않으며, 소비자가 페이로드에 실은 키(예: mid 필드)로 같은 메시지임을 판별하고 걸러낸다.
- 합성체는 중복을 세지도, 걸러내지도 않는다.
- 전체 전송의 수신·중복 판별 주체는 병합 `onMessage`를 직접 읽는 소비자다. 수신측에 JSONTransport를 얹은 경로로 전체 전송을 보내면 동일 tid 중복이 에러(`json.manifest.duplicate`)가 되므로, 전체 전송은 transport를 거치지 않는 프레임에만 쓴다.

## 서버 보장

- 서버측 변경 없음. 기존 서버(에코·중계·connect 핸드셰이크)가 그대로 각 연결을 독립 클라이언트로 다룬다.

## 클라이언트 동기화 계약

- 어떤 소켓의 단절도 다른 소켓 경로의 전송 실패·지연을 유발하지 않는다.
- `sendAll` 확장 호출은 직접 소비자 전용이다. 표준 인터페이스만 아는 상위 계층은 전체 전송의 존재를 알 수 없고 알 필요도 없다.
- 각 소켓의 재연결이 필요하면 주입 전에 기존 재연결 데코레이터로 감싼다. 합성체는 재연결을 소유하지 않는다.

## Out of Scope

- 자동 장애 감지·전환(failover)·메인 자동 승격.
- 모든 소켓에서 유실된 메시지의 복구(재전송·ACK).
- 중복 제거 대행 — 걸러내기는 소비자 책임.
- 경로 간 메시지 순서 재정렬.
- 메시지 단위 수신 출처 태깅.
- 서버측 변경.
- 상위 계층 통합(Peer·JSONTransport 옵션에 multi 개념 추가).
- 소켓 간 상태 동기화·세션 공유.
- 런타임 소켓 추가/제거(구성은 생성 시 고정 — 바꾸려면 합성체를 재생성).

## 재검토 조건

- 메시지 단위로 수신 출처가 필요해지면 → 수신 병합·출처 구분 결정과 00의 구분 요구를 재검토.
- 표준 인터페이스 위에서 전체 전송이 필요해지면(상위 계층 통합 요구) → 전체 전송 단위 결정을 재검토.
- 백업 소켓의 자동 승격이 필요해지면 → 00 비목표(자동 failover)부터 재검토.
- 런타임에 소켓을 추가/제거해야 하면 → 구성 고정 결정을 재검토.
- 수신측 중복 제거를 라이브러리가 대행해야 하면 → 중복 판별 계약을 재검토(수신 데코레이터로 확장 가능).
